ACCEPTANCE TESTS — THE PLATFORM IS NOT COMPLETE UNTIL THESE ARE VERIFIED

Authentication and authorization:
- A user can register, sign in, sign out, and access only their own authorized resources.
- Requests without valid authentication are rejected where authentication is required.
- A user cannot read, change, stop, inspect, or delete another user's project by changing an ID in a URL or API request.
- Administrative operations require explicit administrator authorization and are audit logged.

Plans and enforcement:
- A new free account receives the configured default free entitlements, initially 512 MB RAM and 1 GB storage.
- The server rejects a deployment that exceeds the user's RAM, CPU, storage, transfer, process, or workload limits, even if the client manually edits the request.
- Changing a plan in the admin panel updates the authoritative entitlement without requiring source-code edits.
- Resource usage shown in the dashboard is derived from backend records, not hardcoded sample values.

Deployment lifecycle:
- A supported project can be uploaded or connected, inspected, validated, assigned a plan, scheduled, provisioned, health-checked, and shown as live only after successful verification.
- A failed build or container start produces a useful error state and logs rather than a fake success animation.
- Start, stop, restart, redeploy, and delete operations update both control-plane state and actual worker state.
- Repeated requests do not accidentally create duplicate workloads; long-running actions use jobs and idempotency where appropriate.

Scheduling and capacity:
- A worker with insufficient unreserved resources is not selected.
- Resource reservations are atomic or otherwise concurrency-safe so simultaneous deployments cannot over-allocate capacity.
- Unhealthy or disconnected workers are excluded from new placement until healthy again.
- The scheduler records why a workload could not be placed and returns an understandable error.

Storage and networking:
- A workload's persistent files survive a container restart.
- Persistent data is not treated as permanently tied to ephemeral container storage.
- Storage quota checks occur on the backend.
- Network usage is measured by trusted infrastructure or worker-side instrumentation.
- Domains and HTTPS are shown as active only after verification and successful routing/certificate setup.

Monitoring and recovery:
- CPU, RAM, storage, network, uptime, logs, and workload state are populated from real telemetry when infrastructure is connected.
- A worker disconnect or container crash is recorded and handled according to the configured policy.
- Reconciliation detects control-plane/worker state mismatches and resolves or surfaces them safely.
- Repeated failures do not create endless restart loops.

Security:
- Customer workloads do not receive the host Docker socket or unrestricted host filesystem access.
- Secrets are not exposed in API responses, frontend bundles, logs, or error traces.
- Upload paths and archive extraction are protected against traversal and unsafe file handling.
- API rate limits and input validation are active on sensitive endpoints.
- Worker-to-control-plane communication is authenticated and authorized.

Operations:
- The documented local setup works from a clean environment using the supplied configuration example.
- Database migrations run successfully.
- Background workers and queues can be started and their health observed.
- The README distinguishes local/development mode from production infrastructure.
- Production instructions cover TLS, secrets, database, queue, worker installation, network ports, backups, monitoring, and recovery.

Before choosing final resource limits, inspect the actual development PC's OS,

LOCAL DISK AND STORAGE REQUIREMENTS

- Use my existing internal SSD/HDD; do not require a separate storage provider
  for the initial release.
- Configure a clear storage root directory on the local disk, with separate
  subdirectories or volumes for application data, customer files, workload
  volumes, build cache, database data, logs, and backups.
- Keep PostgreSQL data separate from customer-upload directories. Use normal
  filesystem permissions and volume boundaries; do not let workloads browse the
  database directory or another customer's files.
- Do not count PostgreSQL files, logs, build cache, reserved system space, and
  customer data as if all of them were freely available customer storage.
- Calculate usable storage from real disk capacity and free space. Reserve a
  configurable safety margin for the OS, database, logs, image layers, updates,
  and emergency operations. Never allocate the full physical disk to customers.
- Enforce per-account, per-project, and per-workload storage quotas on the
  backend. Validate archive extraction, file paths, file sizes, and disk usage.
- Handle disk-full conditions safely: stop accepting new allocations, show a
  clear alert, preserve database integrity, and avoid corrupting existing data.
- Persistent workload data must survive normal container restarts and rebuilds.
- Make the storage layer replaceable later with a storage server or S3-compatible
  service without rewriting all business logic.
- Local backups on the same disk are useful for recovery from some mistakes but
  are NOT protection against disk failure, theft, fire, or total PC failure.
  Document and support export/off-site backup to a separate device or location.
  Do not claim backups are safe until a restore test succeeds.

Stage 4 — Add worker servers:

RESOURCE SCHEDULING ON A SINGLE PC

The scheduler must distinguish physical capacity from capacity available to
customer workloads. Reserve configurable CPU/RAM/disk headroom for the OS,
frontend, API, database, queue, Docker, logs, builds, monitoring, and emergency
operations. Query actual worker capacity where possible. Do not allocate the
same RAM, CPU, or disk space to multiple workloads as though it were unreserved.

The 512 MB RAM / 1 GB storage free plan describes a customer's maximum
entitlement, not a guarantee that every account can run simultaneously. The
scheduler must check both the account's entitlement and actual remaining host
capacity before deployment. If capacity is unavailable, queue or reject the
deployment with a clear reason rather than overcommitting silently.

Make per-workload CPU, memory, process, disk, file-size, runtime, concurrency,
build-resource, and network limits configurable and enforce them at the backend
and runtime layers where supported. Clearly distinguish hard-enforced limits
from estimated or not-yet-implemented measurements.

SECURITY REQUIREMENTS FOR A PERSONAL PC HOSTING WORKLOADS

Treat arbitrary customer code as hostile. A container alone is not a guarantee
against all isolation failures. Do not run customer workloads with privileged
container mode, host networking, host filesystem mounts, Docker socket access,
or unrestricted Linux capabilities. Use non-root containers and hardened
runtime defaults where supported. Apply seccomp/AppArmor or equivalent controls
where available, drop unnecessary capabilities, isolate networks, block access
to host services and cloud/local metadata endpoints, and limit outbound traffic
where feasible.

Do not allow public users to run arbitrary privileged Docker images or arbitrary
host commands. Add quotas, rate limits, account verification appropriate to the
risk, abuse reporting, suspension tools, audit trails, and a documented response
process. For a first public release, it is acceptable to limit supported runtimes
and image sources rather than pretend unrestricted secure hosting is complete.

Do not store uploaded projects or execute builds as the same unrestricted user
that administers the PC. Do not place secrets in images, logs, source control,
or client-side bundles. Keep administrative interfaces private and protected
with strong authentication.
